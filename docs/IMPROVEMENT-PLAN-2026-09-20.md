## 1. 结论：部分同意原评分，但不继续使用单一总分

原结论“能力内核接近 8 分、用户可感知闭环约 7 分”方向上成立；原综合分 `7.6/10`
可以作为代码与能力成熟度的粗略快照，但不能作为产品是否准备好的判断。它有三处需要修正：

1. **把实现成熟度与真实用户验证混在了一起。** Strategy Distillation 的代码路径已经完整，
   但 `PLAN.md` 和产品 RFC 都明确记录“待真实用户产品验收”。
2. **把主动排除的能力当成低分项。** 任意自然语言策略编译和通用策略回测不在第一版产品合同内，
   应标为 `N/A / 延后评审`，而不是用 `4.5` 或 `5.5` 拉低核心产品评价。
3. **监测问题先要验证产品承诺，再决定技术形态。** 缺少内置 scheduler 是事实，但“因此下一步就
   建 scheduler”是方案推断。应先证明用户需要脱离宿主持续运行，并完成一次可信的监测生命周期。

### 修订后的双评分

| 评价面 | 修订评分 | 依据与限制 |
|---|---:|---|
| 能力与工程成熟度 | **7.8 / 10** | 后端、Agent/MCP、数据和权限边界扎实；格式门禁与前端发行物仍漂移 |
| 真实用户验证完成度 | **6.4 / 10** | 主流程已实现，但没有真实用户完成“提炼 → 修正 → 保存 → 新会话复用 → 可选监测” |

单一综合分不再作为阶段 Gate。后续只用“用户完成事件是否发生”和“产品承诺底线是否通过”判断进度。

## 2. 方向约定

## 3. MVP

以下阶段按顺序执行。每个阶段只有在用户可观察验收通过后才能进入下一阶段。

### 阶段 0 — 建立可信基线

**用户结果：** 用户拿到的安装产物与仓库声明一致，团队对“当前真的能做什么”没有冲突口径。

工作项：

- 修复并验证 `web/dist` 与 `src/mommy_chaogu/web/static` 一致性。
- 清理当前 14 个 format check 失败，不扩大为无关重构。
- 固化一份真实用户验收脚本，材料必须来自用户自己的方法或文章，不使用仅为测试设计的 fixture。
- 在验收记录中分别报告实现成熟度与用户验证完成度，不再回填单一总分。

**用户验收演示：** 从干净安装或受支持 Agent 连接进入，能看到与当前源码一致的入口；验收者可读懂
即将执行的真实场景、权限和停止条件。

**Gate：** 发行物一致性和 format check 通过；真实验收材料与观察记录模板就绪。测试通过只能证明
可以进入下一阶段，不能代表产品价值通过。

### 阶段 1 — 完成一次真实策略蒸馏闭环

**用户结果：** 用户把自己的方法交给 Agent，在一轮自然语言体验中看懂、修正、确认并保存；新会话
能找回并按同一方法查看一个真实标的。

工作项：

- 选择一份用户真实关心的材料，走完来源保真、策略卡生成和最多一次成组澄清。
- 记录用户主动修正了什么，以及系统是否准确保留原意；不以 schema 正确替代此记录。
- 用户明确确认后保存；新会话找回来源、版本和修改说明。
- 对一个真实标的逐条件输出“满足 / 不满足 / 无法判断”，同时显示证据时间与缺口。
- 若用户不理解或不愿复用，只修改这条体验，不扩建通用 runtime、回测或新前端。

**用户验收演示：** 用户能够复述这张策略卡的含义，指出至少一处自己确认或修改的内容，并在新会话
用一句“按这套方法看 X”获得逐条件结果。

**Gate：** 用户明确表示卡片忠于原意、愿意保存并能再次使用；失败则停留在阶段 1。

### 阶段 2 — 交付可信的策略到监测闭环

**用户结果：** 用户把策略卡中一个真正受支持的条件变成监测，知道它何时运行、最后检查时间、数据
来源、为何触发以及如何停止；不支持条件仍保留为人工项。

工作项：

- 先定义可承诺的运行模式：前台有界循环、宿主调度或独立后台，不能含糊称为“持续运行”。
- 为选择的主入口展示 `运行状态 / 最后检查 / 下一次检查 / 数据新鲜度 / 停止方式`。
- 加入交易时段与休市语义，避免使用昨收快照制造夜间“实时”提醒。
- 验证二次确认、触发解释、通知、停止和重启恢复；记录失败时用户会看到什么。
- 只有在用户明确需要“宿主关闭后仍运行”时，才决定是否建设内置 scheduler/daemon。

**用户验收演示：** 用户亲自把一个价格或涨跌幅条件启用为监测，看到一次当前检查或可解释触发，
随后停止它并验证不再运行。

**Gate：** 用户能回答“它现在是否运行、上次何时检查、为什么提醒、怎么停”；不发生非交易时段误报。

### 阶段 3 — 主入口发布演练

**用户结果：** 新用户在一个受支持的外部 Agent 中，不配置第二套项目 LLM Key，就能完成连接、权限
理解和阶段 1 或阶段 2 的第一次有用结果；失败时有明确恢复路径。

工作项：

- 以 Agent-managed 路径为主入口完成一次干净环境安装与 MCP 真实探针。
- 默认保持 `market-only`，只在策略保存或监测需要时解释并请求扩大权限。
- 验证超时、数据源降级、旧数据保留、发行物与文档口径。
- 将阶段 1/2 的用户完成事件纳入发布 checklist；不以 tools-list 成功替代。

**用户验收演示：** 新会话从连接计划开始，用户看懂将修改的文件和权限，完成一次真实结果并知道下一步
如何修正或复用。

**Gate：** 干净环境演练通过；项目才从 Linear `Planned` 进入执行/发布状态。

## 4. Extensions

- **内置 scheduler / daemon：** 仅在阶段 2 证明用户需要脱离宿主持续运行后进入。**You can ignore this for now.**
- **Web、TUI、DSH 全入口体验一致性：** 主入口闭环通过后，再统一 loading/empty/error/stale/source/as-of 语义。**You can ignore this for now.**
- **通用策略回测：** 只有 point-in-time 数据、复权、信号、组合构造和评价方法满足 RFC 进入条件时才独立立项。**You can ignore this for now.**
- **任意自然语言策略编译或 DSL：** 当前会扩大安全与语义风险，且不属于已确认用户结果。**You can ignore this for now.**
- **跨数据源与上下文装配重构：** 只有当它阻塞上述用户验收或导致现实故障时再排入对应阶段。**You can ignore this for now.**

## 5. Linear 结构

Linear 项目 `mommy-chaogu` 使用四个里程碑，与本文件阶段一一对应：

| Milestone | 结果 | 核心 Issues |
|---|---|---|
| M0 · 可信基线 | 发行物和验收口径可信 | 发行物一致性；format 门禁；真实验收脚本 |
| M1 · 真实策略闭环 | 用户完成提炼、保存、找回、复用 | 真实材料验收；记录修正与结果；闭环复盘 |
| M2 · 可信监测闭环 | 用户看懂并控制一个真实监测 | 运行合同；交易时段与生命周期；端到端验收 |
| M3 · 主入口发布演练 | 干净 Agent 环境完成第一次价值 | 安装与权限演练；降级恢复；发布 Gate |

所有 Issues 初始保持未开始；本计划同步到 Linear 不代表开始实施。Extension 不建立当前执行 Issues，
只保留进入条件，避免形成虚假 backlog。

## 6. 成功与停止规则

- 每阶段先展示用户结果，再报告工程检查。
- 任何阶段若只能证明“代码存在、测试通过、工具可见”，均不得标记完成。
- 用户不能理解或复用结果时，优先缩短路径和修正文案，不扩大架构。
- 数据、算法或时间语义不足时，降级为 `manual / unavailable`，不得创造代理指标。
- 没有阶段 1 的真实用户证据，不启动回测、DSL、新前端或通用平台工作。
