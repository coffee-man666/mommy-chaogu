# Agent-managed Strategy Distillation RFC

> 状态：Approved direction / 第一版实现完成，待真实用户产品验收
> 初版：2026-08-06
> 纠偏：2026-08-11
> 目的：定义用户可感知的策略沉淀闭环、当前资源边界和验收方式。

## 1. 产品提议

mommy-chaogu 的下一阶段主线是：

> **一套可以被用户现有 Agent 接管的本地投研能力。用户把文章、研报、自然语言观点或自己的
> 方法交给 Agent；Agent 将其整理成忠于原意、可修改、可保存、以后能再次使用的策略卡，并在
> 当前能力范围内结合实时证据应用和监控。**

这是 Strategy Distillation（策略沉淀），不是自动策略生成，也不是回测平台。

```text
文章 / 研报 / 用户方法
        ↓
宿主 Agent 保留来源并提炼策略卡
        ↓
标明 supported / manual / unavailable
        ↓
至多一次重要澄清 → 用户自然语言修正并确认
        ↓
本地保存
        ↓
“按这套方法看 X 今天”
        ↓
现有 research_* 证据 + 逐条件判断
        ↓
可选：支持条件生成监控候选 → 用户二次确认启用
```

## 2. 为什么这样收束

项目已有行情、资金流、持仓、记忆、监控、MCP 和 Coding Agent 连接能力。真正缺少的不是新的
通用运行时，而是让用户把自己的研究方法留下来，并在之后自然复用的体验。

此前 Draft RFC 把“策略沉淀”过早收缩为 `ExperimentSpec → 回测 → Golden Scenario`，导致：

- 临时验证场景替代了产品本身；
- 技术 gate、hash 和回测包装先于来源接收、用户确认、保存和日常复用；
- 在数据复权、历史语义和组合方法尚未准备好时，产生了不能承担用户信任的“回测”结果；
- 工程完成度被误当成用户完成度。

本次纠偏取消 Golden Scenario 和回测作为交付门槛。相关历史仍保留在 Git 中，不继续出现在当前
产品计划和用户路径中。

## 3. 第一目标用户与核心任务

第一阶段服务会阅读市场观点、研报或交易方法，希望让自己的 Agent 帮忙整理和持续使用，但不想
学习 MCP、数据库、因子语言或回测框架的投资者。

核心任务：

1. “帮我把这篇文章里的方法整理清楚。”
2. “这是我自己的观察框架，帮我记下来。”
3. “按上次保存的方法看看这只股票今天是什么状态。”
4. “能自动提醒的部分帮我准备一个监控，先让我确认。”

用户不需要知道策略卡的 JSON 结构。Agent 应始终先展示人类可读版本。

## 4. 用户完成事件

一次策略沉淀只有在以下事件发生后才算完成：

- 用户看到来源和原始意图没有被替换；
- 用户看懂方法摘要、适用对象、观察条件和失效条件；
- Agent 明确说明每项条件现在能否自动检查及原因；
- 用户用自然语言修正并明确确认；
- 用户选择保存后收到可找回的本地回执。

代码、schema、测试、hash 或一次工具成功调用都不能单独完成该事件。

## 5. 策略卡

策略卡是用户文档和本地记忆，不是通用执行 DSL。第一版字段：

```yaml
title: 一眼能懂的名称
source:
  type: text | file | url | conversation | other
  title: 来源名称
  reference: 文件路径、URL 或用户描述
  content_hash: 可选；只在确实哈希过内容时用于本地去重与溯源
  hash_scope: full_source | supplied_excerpt  # 与 content_hash 同时出现
  excerpts: 少量关键原文
original_intent: 用户原始目标
summary: Agent 对方法的简明复述
applies_to: [适用市场、标的或场景]
conditions:
  - id: stable-id
    category: observation | entry | exit | risk | context | invalidation
    statement: 人类可读条件
    automation: supported | manual | unavailable
    reason: 为什么能或不能自动检查
    evidence_tools: [当前可用工具]
    monitor_rule: null | {condition, threshold}
assumptions: []
limitations: []
```

约束：

- `supported` 只表示现有工具能提供所需当前证据，不表示策略有效或一定盈利；
- `manual` 表示需要图形判断、主观解释或当前没有确定性实现；
- `unavailable` 表示缺少必要数据或工具；
- Agent 不为提高“自动化率”而把原规则改写成方便实现的替代规则；
- monitor rule 第一版只接受现有告警系统支持的价格高于/低于、涨跌幅高于/低于。

## 6. Agent、Skill 与后端分工

### 6.1 宿主 Agent

- 读取用户已经提供或授权访问的文本、文件和 URL；
- 理解语义、保留关键原文、区分作者事实与 Agent 解释；
- 生成可读策略卡并只提出会改变含义的问题；
- 使用现有研究工具收集当前证据并逐条件解释；
- 不调用项目内第二个 LLM 完成同一轮提炼。

### 6.2 `mommy-strategy` Skill

- 规定来源、提炼、澄清、确认、保存、应用和监控流程；
- 定义支持矩阵与用户输出形状；
- 禁止未经确认保存、未经二次确认启用监控；
- 明确禁止把策略沉淀自动升级为回测或收益承诺。

### 6.3 本地后端

- 校验并保存已确认策略卡；
- 提供 list/get/archive 和版本记录；
- 返回可用的监控候选，不解释投资意义；
- 继续通过现有 `research_*` 和原子工具提供当前证据；
- 不抓取任意网页、不内置第二个 LLM、不编译任意策略代码。

## 7. 隐私与授权

- 公开行情研究可在 `market-only` profile 使用；
- 策略卡、来源摘录、个人修订属于个人数据，只在 `personal` profile 暴露；
- 未确认的草稿不写入本地数据库；
- 保存需要一次明确确认；监控启用需要独立的第二次明确确认；
- Agent 不绕过 MCP/工具直接读取个人数据库；
- 用户说“不保存”时，来源和草稿仅留在当前对话上下文。

## 8. 当前支持边界

### 8.1 当前可用

- 宿主 Agent 可读取的纯文本、本地文件和 URL；
- 当前报价、K 线、资金流、板块、基本面、公告和研究证据包；
- 本地 SQLite 策略卡存储；
- 价格和涨跌幅四类监控条件；
- Agent Skills + MCP 接入；外部 Agent 承担推理。

### 8.2 当前不承诺

- 任意自然语言规则自动编译；
- 通用因子/策略 DSL；
- 参数优化、自动荐股或交易执行；
- 真实历史回测、Walk-forward、Regime、Sharpe 或组合收益；
- 对文章中所有数据或主观判断自动验证；
- 新 Web 策略编辑器。

独立 `ma-suppression-monitor` 包可以作为权威方法来源，但在其数据输入口径与主程序可靠接通前，
EMA/ATR/通道条件应标为 `manual` 或 `unavailable`，不得用 SMA20 等方便实现的规则替代。

## 9. 第一版纵向场景

用户提供一段带有若干观察条件和风险条件的方法。Agent 应：

1. 展示来源名称和关键摘录；
2. 用用户语言生成一张策略卡；
3. 对无法自动检查的内容明确标注，不猜测；
4. 只在含义确有歧义时做一次成组澄清；
5. 根据用户修改重新展示最终卡片；
6. 得到“保存”确认后调用本地保存能力并返回名称、ID 和版本；
7. 在新会话中找回该卡；
8. 针对用户指定标的调用现有研究工具，输出每项条件的“满足 / 不满足 / 无法判断”；
9. 如果存在四类受支持监控规则，展示 candidate；用户再次确认后才创建告警。

## 10. 验收标准

- 从提供材料到第一张策略卡不超过 3 分钟；
- 最多一次成组澄清，用户全程使用自然语言；
- 用户能指出卡片是否忠于原意并完成修改；
- 未确认不保存，重复保存不会静默制造副本；
- 新会话能找回来源、当前版本和修改说明；
- 应用结果逐条件给出当前证据、时间和缺口；
- 所有条件都有 `supported / manual / unavailable`；
- 不把缺少数据或算法的条件伪装为自动化；
- 监控候选与启用分离，并有二次确认；
- 外部 Agent 模式不要求第二套项目内 LLM key；
- 回测、通用 runtime、发布矩阵和新前端均不是第一版验收项。

## 11. 后续能力的进入条件

历史验证只有在独立评审确认以下资源后才能成为可选能力：

1. 调整一致的 OHLCV 与公司行动处理；
2. 明确的 point-in-time 与交易日历语义；
3. 权威且经用户确认的信号、入场、退出和组合构造；
4. 足够样本与可解释的基准、成本和评价方法；
5. 能向用户清楚说明局限，而不是只生成技术指标。

缺少任何一项时，只能提供当前状态评估或探索性观察，并按真实名称展示。
