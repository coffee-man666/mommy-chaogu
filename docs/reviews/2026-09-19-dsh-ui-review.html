产品方向与交付评审 — mommy-chaogu DSH UI

把 DSH UI 的下一条用户结果定义为：用户能在一次小范围投研中看懂自选对象、证据、来源/时间/新鲜度，并继续追问或请求加入自选；不会把“没有数据”误读成“没有结果”。

推荐：以方案 C「对话原生证据链」为骨架，以方案 A「决策摘要带」为默认密度。保留官方 slot、固定右缘 dock 和服务端计算边界；方案 B 只在验证后做受限实验，方案 D 不作为默认方向。

本次是审核建议，不是已批准的产品路线。决定性未知：用户是否首先需要小范围、多证据研究，还是频繁需要多标的比较；以及 DSH slot 是否提供可靠的 composer、导航和调用身份接口。

1. 下一步建议

当前 build、typecheck 和 95 个 DSH bundle 测试均通过，工程边界稳定。但用户体验仍偏向“工具卡片集合 + 自选列表”，而不是“扫描 → 取证 → 行动”。继续增加卡片或图表模式不能解决事实状态和下一步行动不清的问题。

R1 · 先修事实状态

可见区分 loading、empty、ready、partial、stale、error；已有快照失败时保留并提示；逐标的显示 missing/stale、来源和时间。

R2 · 让卡片成为证据

quote / bars / flow 先统一证据头、2–4 个摘要事实和明确空/错态，再扩展其他卡片。

R3 · 打通下一步

确认宿主动作能力后，建立标的焦点与 follow-up intent；写入自选永远回到 Agent 审批链。

当前代码中的关键缺口：dock.tsx:36,216,237-246；dock.tsx:113-119,221-250,322-330；cards.tsx:109-150,328-335,391-396,470-475,503-508,539-544。

4. 路线判断

是否兑现既定方向：承重边界已经兑现；dock 和卡片基础能力部分兑现；“用户看懂结果并继续修正或复用”尚未被当前 UI 验收证明。历史测试证明工具能调用、回答能诚实说明限制，但不能替代 rich card 的真实使用证据。

方向假设是否成立：对话 + 上下文 dock + 证据卡与项目定位一致；用户是否需要筛选/排序/多选比较仍未验证。不能把“13 张卡”本身当成产品目标。

最小实验：已有多个分组自选，其中一只报价正常、一只 stale、一只缺失；用户问“今天谁值得继续看，为什么，数据是否过期”。如果用户主要卡在跨标的比较，再开启 B；如果主要卡在判断数据是否最新，继续做比较没有优先级。

5. 四个界面方向

方案 A · 极简「决策摘要带」

默认只放名称、代码、价格、涨跌、状态和一条注意标签，一次展开一个标的；卡片默认 2–4 个事实，明细渐进披露。学习成本最低，但摘要更容易被误读。

type Freshness =
  | { kind: 'fresh'; source: string; asOf: string }
  | { kind: 'stale'; source?: string; asOf?: string; reason: string }
  | { kind: 'missing'; reason: string }

方案 B · 有边界的「研究工作台」

增加搜索、分组筛选、排序、临时固定和有限多选比较；明确区分“研究固定”和“加入自选”。灵活但会把对话辅助面推向通用后台，应等验证后再做。

interface ResearchViewState {
  query: string; group: string | null
  sort: 'group' | 'changePct' | 'freshness'
  locallyPinned: Set<string>; selected: Set<string>
}

方案 C · 对话原生「证据链卡」

AI 叙述提出判断，卡片证明、对比或限定，dock 只保持“我正在看谁”。每张卡统一 subject、source、as-of、freshness、scope、caveat 和下一步；没有可靠调用身份时不猜关系。

interface EvidenceNode<T> {
  nodeId: string; chainId?: string
  subject: { code: string; name: string }
  role: 'quote' | 'market-context' | 'bars' | 'flow'
  provenance: { source: string; asOf?: string
    fetchedAt?: string; freshness: 'live'|'cached'|'stale'|'unknown' }
}

方案 D · 专业「密集型行情终端」

借鉴表格密度、数字对齐和键盘导航，但会把 stale、caveat、探索性回测放进“交易终端”语境，容易让红绿、胜率和信号看起来像结论。只借鉴排版和导航，不采用其产品形态。

合成结论：C 提供证据语义，A 提供默认展示密度，B 只作为验证后的有限能力，D 只借鉴键盘和数字排版。推荐 C+A。

6. 建议与取舍

R1 · 先让 watchlist 与卡片的事实状态可见

最小动作：建立 loading / empty / ready / partial / stale / error；修复初始加载优先级、空态刷新、已有快照的列表错误提示；逐代码显示 fresh/stale/missing、source、as-of、reason。

为什么现在：这是事实诚实性的产品底线。验证应注入首次加载、真空、列表失败但有旧条目、报价失败但有旧报价、部分缺失五态；用户应能指出“是否存在、哪只不可用、最后有效时间、如何重试”。高信心。

R2 · 把 13 张卡收敛成「摘要 + 证据头 + 明确结果状态」

最小动作：先为 quote / bars / flow 增加统一 EvidenceHeader；默认只呈现 2–4 个决策事实，详情渐进披露；有效空结果、error、unsupported 分开渲染，只有 unsupported 回落通用行，回测 caveat 保持可见。

为什么现在：继续新增卡片会放大工具适配器漂移。用“600519 为什么跌”验证用户是否能说出判断、来源/时间和缺口；中高信心。

R3 · 宿主动作能力确定后，建立「标的焦点 → 下一步」闭环

最小动作：先做只读 SymbolRef 和 action intent：focus-symbol、expand-detail、ask-follow-up、request-watchlist-add。若宿主没有官方 action，显示可复制追问提示，不造私有 RPC；写入自选永远回到 Agent 审批。

为什么现在：没有下一步，卡片只是结果终点；但动作接口尚未证实。验证“继续看 600519 的 20 日趋势”是否保留代码与语境，以及审批、回执、SSE、dock 计数是否一致。中等信心。

7. 下一阶段与暂缓项

  1. 先做 R1：状态诚实性与故障恢复；若用户仍无法判断空、stale、missing、error，不进入比较功能。
  2. 再做 R2：quote/bars/flow 的证据头与空结果卡；复用现有 slot 和服务端口径。
  3. 然后探测 R3：确认官方 composer/navigation/action seam，再做焦点和 follow-up；缺失时收窄为提示。
  4. 最后做方向决定：只有真实任务显示比较是主要阻塞，才做搜索 + 单一排序 + 临时选择的 B 版本。

暂缓：全量研究工作台、任意列/复杂筛选/多层比较/自由拖拽，以及更多 card 类型和图表变体。

停止作为默认方向：独立交易终端、单键交易、闪烁式实时反馈、浏览器端均线/复权/信号/回测计算。
