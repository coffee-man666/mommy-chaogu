# 产品方向与交付评审 — mommy-chaogu DSH UI

2026-09-19 · 范围：DSH 浏览器半、右缘 watchlist dock、`tool.call.toolview` 数据卡 · revision：`192ee5214e02d272fc8e285c4ab9abce5282f242` · 工作树：未跟踪 `docs/notes/`、`docs/project-intro.html`，不属于本次范围，未修改。

## 推荐下一步

建议把 DSH UI 的下一条用户结果定义为：

> 用户问“比较我的自选今天的表现，找一只值得继续研究的标的；如果数据过期，告诉我”，在一个对话屏幕内看懂自选对象、证据、来源/时间/新鲜度，并能继续追问或请求加入自选，不必手动重新输入代码，也不会把“没有数据”误读成“没有结果”。

推荐采用 **方案 C「对话原生证据链」作为骨架 + 方案 A「决策摘要带」作为默认密度**。保留当前官方 slot、固定右缘 dock 和服务端计算边界；暂不把 DSH 做成独立行情终端。方案 B 的筛选/比较能力只在单标的闭环验证后作为有边界的实验；方案 D 不作为默认方向。

为什么现在做这件事：当前工程门禁稳定，dock 已具备分组、展开、收起和 SSE 重拉基础，但用户路径仍是“工具卡片集合 + 自选列表”，不是“扫描 → 取证 → 行动”。代码中还有会改变事实含义的状态缺口：初始加载会落入空态、空自选没有刷新按钮、已有旧条目时 watchlist 请求错误不显眼；多类卡片对有效空结果直接不渲染，且卡片普遍缺少统一来源、时间和新鲜度。继续增加卡片数量或图表模式不能解决这些问题。

本次决定仍是审核建议，不是已批准的产品路线。决定性未知是：真实用户是否首先需要小范围、多证据研究，还是会频繁要求多标的筛选/比较；以及 DSH slot 是否提供足够可靠的 composer、导航和调用身份接口来承载卡片动作。

## 路线判断

### 是否兑现既定方向

- **已兑现：** 宿主不改源码、官方 `shell.overlay` / `tool.call.toolview` slot、TS 不计算市场指标、服务端 MA 原样渲染、写操作仍有回执和 SSE 基础。这些是工程边界，不等同于用户价值，但它们为正确的 UI 方向提供了可靠承重面。
- **部分兑现：** 右缘 dock 能作为自选索引，数据卡能展示报价、资金流、K 线、信号、回测等结果；然而来源/时间/状态未形成统一证据头，下一步行动未形成闭环。
- **未兑现：** “用户看懂结果并继续修正或复用”尚未被当前 UI 验收证明。历史测试证明了工具能被调用和回答能诚实描述限制，但 T3 的卡片视觉展开受阻，且没有真实用户任务观察。

### 方向假设的有效性

- **支持：** 对话 + 右缘上下文 dock + 工具结果卡符合项目已确认的本地投研工具定位；官方 slot 和服务端计算边界稳定。
- **未验证：** 默认用户是否需要筛选、排序、多选比较；没有用户行为数据，不能把“研究工作台”直接升格为路线。
- **需要收窄：** “13 张独立卡片”不是产品目标；若卡片继续只增加字段和模式，用户仍无法判断证据是否可靠或下一步做什么。

最小实验是同一条任务的故障注入版：已有多个分组自选，其中一只报价正常、一只报价 stale、一只缺失；用户询问“今天谁值得继续看，为什么，数据是否过期”。观察用户是否能在不读原始 JSON、不重新输入代码的情况下指出一个对象、一个证据、一个时间/来源状态和一个下一步。若用户主要卡在跨标的比较而不是状态理解，再开启方案 B；若用户主要卡在“这是不是最新数据”，继续扩展比较能力没有优先级。

## 设计两次以上：四个界面方向

### 方案 A：极简「决策摘要带」

适用场景是开盘后或刚进入 DSH 时，30 秒内扫描自选并挑一个继续研究。默认行只显示名称、代码、价格、涨跌、服务端状态和一条注意标签；一次只展开一个标的；卡片默认呈现 2–4 个事实，更多字段进入明细。

```ts
type Freshness =
  | { kind: 'fresh'; source: string; asOf: string }
  | { kind: 'stale'; source?: string; asOf?: string; reason: string }
  | { kind: 'missing'; reason: string }

interface DecisionRow {
  symbol: { code: string; name: string }
  price?: number
  changePct?: number
  freshness: Freshness
  attention?: string
}
```

它把“如何从不同工具挑摘要、如何区分 stale 与空结果、如何回到宿主确认链”隐藏在适配器内。优点是学习成本最低、屏幕占用最小；代价是摘要更容易被误读，明细入口必须可发现。明确不要把它扩成第二个终端，也不要在 TS 计算异常或指标。

### 方案 B：有边界的「研究工作台」

在当前 dock 上增加搜索、分组筛选、排序、临时固定和有限多选比较；区分“研究固定”（浏览器视图状态）和“加入自选”（持久化写操作）。卡片中的同一代码可以高亮 dock 行，用户把一批结果缩小成下一轮研究集合。

```ts
interface ResearchViewState {
  query: string
  group: string | null
  sort: 'group' | 'changePct' | 'freshness'
  locallyPinned: Set<string>
  selected: Set<string>
  openCode: string | null
}
```

它隐藏本地视图状态、跨卡片对齐和比较集合管理。灵活性最高，但“当前选中 / 研究固定 / 真实自选”容易混淆，也会把 264px dock 推向后台化。只有在方案 A/C 的单标的闭环验证显示比较是主要阻塞时才值得做。

### 方案 C：对话原生「证据链卡」

AI 叙述提出判断，卡片逐个证明、对比或限定，dock 只保持“我正在看谁”。每张卡统一显示 subject、role、source、as-of、freshness、scope、caveat 和最多三类下一步动作；卡片之间只在服务端/宿主提供可靠调用身份时表达 chain/relation，不能由 TS 按出现顺序猜关系。

```ts
interface EvidenceNode<T> {
  nodeId: string
  chainId?: string
  subject: { code: string; name: string }
  role: 'quote' | 'market-context' | 'bars' | 'flow' | 'history' | 'conclusion'
  relation?: 'supports' | 'contrasts' | 'limits' | 'background'
  payload: T
  provenance: {
    source: string
    asOf?: string
    fetchedAt?: string
    freshness: 'live' | 'cached' | 'stale' | 'unknown'
    scope?: string
    frequency?: string
    adjustment?: string
    timezone?: string
  }
  caveats: string[]
}
```

它隐藏跨语言 provenance、时间口径和错误状态，但不隐藏这些信息本身。优点是最符合“行情与证据”产品承诺；代价是每张卡会变高，且宿主 slot 若没有 `callId/turnId`，只能降级成“同一标的证据集合”。这是本评审推荐的骨架。

### 方案 D：专业「密集型行情终端」

借鉴表格密度、数字对齐、键盘导航、多标的快速扫描，适合熟悉行情软件的用户。它会把 dock 和卡片都做得更高密度，强调筛选、比较和键盘效率。

它隐藏列布局、快捷键和批量状态，但把 stale、caveat、探索性回测与普通行情放在同一终端语境中，容易让红绿、胜率和信号看起来像交易结论。对当前产品定位而言，它会扩大认知和兼容风险；应作为明确拒绝的默认方向。可以借用数字对齐和键盘导航，不能借用单键下单、闪烁实时性或浏览器指标计算。

### 方案比较与合成

方案 A 的接口最浅、最容易正确使用，但必须依赖统一状态和来源元数据，否则“摘要”只是更短的误导。方案 B 最灵活，却把一个对话辅助面推向通用后台；在没有用户证据前不应先建。方案 C 的界面复杂度较高，但它把真正需要隐藏的复杂度——证据的来源、时间、口径、缺口和限制——集中在一个可复用边界内，且仍能保持 dock 很窄。方案 D 在密度上最强，却最容易违反“不把探索性观察包装成交易终端”的边界。

因此合成方向是：**C 提供证据语义，A 提供默认展示密度，B 只作为验证后的小范围视图能力，D 只借鉴键盘和数字排版，不借鉴终端产品形态。**

## 建议

### R1 · 先让 watchlist 与卡片的事实状态可见

- **服务的结果 / 假设：** 兑现“真实行情证据必须说明新鲜度和缺口”（方向依据核心价值，文档声明）；防止用户把空列表、旧值和无命中混为一谈。
- **旅程缺口与证据：** `dock.tsx:36` 的初始 `loading` 没有独立渲染分支；`dock.tsx:216` 使空自选没有刷新按钮；`dock.tsx:113-119` 保存了已有条目但 `dock.tsx:221` 只有在条目为空时才显示错误；报价 stale 是批次脚注而非逐标的状态。当前是代码检查证据，空库/断桥真机复现尚未完成。
- **最小动作：** 建立 `loading / empty / ready / partial / stale / error` 的可见状态模型。修复初始加载优先级、空态刷新、已有快照的列表错误提示；逐代码表达 `fresh / stale / missing`，显示 `source + asOf + reason`。没有旧快照时不能写“显示上次快照”。
- **为什么现在：** 这是产品承诺底线；若不先修，后续任何摘要或比较都会建立在错误事实之上。
- **用户可见验证：** 用真实/夹具桥分别注入首次加载、真空、列表失败但有旧条目、报价失败但有旧报价、部分代码无报价五种状态。用户应能指出“自选是否存在”“哪只数据不可用”“最后有效时间”和“如何重试”。
- **工程支持：** 将 dock 的两个请求拆成列表快照和报价快照；桥/服务端提供状态与元数据；为分支加组件或 DOM 状态测试。不得让 TS 自己推断数据源或阈值。
- **取舍与信心：** 增加状态文字和行级标记会降低纯视觉密度，但高信心，因为它直接恢复事实诚实性。

### R2 · 把 13 张卡收敛成「摘要 + 证据头 + 明确结果状态」

- **服务的结果 / 假设：** 用户能回答“这是什么、针对谁、截至什么时候、来自哪里、下一步看什么”（方向依据下一条结果，审核推断，待确认）。
- **旅程缺口与证据：** `QuoteCard` 主要有 timestamp，`QuotesCard`/`IndexesCard` 缺少统一 provenance；多处 `parseX(...).length === 0` 直接 `return null`（`cards.tsx:109-150,328-335,391-396,470-475,503-508,539-544`）；现有历史 GUI 只确认回答诚实，不足以确认 rich card 视觉被用户使用，T3 还明确记录视觉展开受阻。
- **最小动作：** 先只为 quote / bars / flow 做统一 `EvidenceHeader`：标的/范围、source、as-of、freshness、周期/复权（若服务端提供）、caveat。默认只放 2–4 个决策事实，详细字段用渐进披露；有效空结果、error、解析不支持分别渲染。`unsupported` 才回落宿主通用行。回测 caveat 必须保持可见。
- **为什么现在：** 继续新增卡片只会放大 13 个工具适配器的形状和文案漂移；先让已有卡片成为可理解证据，才能验证方向。
- **用户可见验证：** 任务“600519 今天为什么跌？给出报价、指数、日线、资金流证据”。用户在不看原始 JSON 的情况下说出一个判断、一个来源/时间状态和一个缺口；请求 0 命中时看到“0 个命中”，而不是卡片消失。
- **工程支持：** Python/CLI/MCP 返回一个可版本化的证据外壳，TS 只做 `ToolviewResult<T>` 映射；修复 malformed `manage_watchlist` 结果不能默认标为 `ok`。继续保留解析失败不炸 slot 的保护。
- **取舍与信心：** 卡片更高、契约需要跨语言变更；中高信心，因它直接对应项目对来源/时间/缺口的文档承诺，但用户阅读负担需要实验确认。

### R3 · 在宿主动作能力确定后，建立最小「标的焦点 → 下一步」闭环

- **服务的结果 / 假设：** 用户能从证据继续追问、打开明细或请求加入自选，不重复输入代码（方向依据下一条结果，审核推断，待确认）。
- **旅程缺口与证据：** 当前只有 K 线“明细”按钮；dock 行是 `div role=button` 局部展开，卡片没有通用 action；`types.ts:7-16` 的 owner props 没有 `toolName/callId/turnId`。官方 composer/navigation/action surface 目前未证实。
- **最小动作：** 先做只读 `SymbolRef` 和 action intent：`focus-symbol`、`expand-detail`、`ask-follow-up`、`request-watchlist-add`。若宿主无官方 action，就显示可复制的追问提示，不造私有 RPC；加入自选永远回到 Agent 的 `manage_watchlist` 与审批闸门。
- **为什么现在：** 没有下一步，卡片只是结果终点；但不能在动作接口未确认前直接增加按钮。
- **用户可见验证：** 从一个报价/资金流卡选择“继续看 600519 的 20 日趋势”，composer 保留代码与当前证据语境；请求加入自选时出现宿主审批，拒绝不落盘，允许后 `WatchlistOpCard`、SSE 和 dock 计数一致。
- **工程支持：** 先探测/确认 DSH slot 能提供的官方上下文和 composer seam；补键盘焦点、`<button>` 语义、可见 `:focus-visible`、异步 `aria-live`；这些是当前方向的可用性支持，不单独升级成新产品能力。
- **取舍与信心：** 依赖宿主接口，若缺失则只能做提示型降级；中等信心，需一条真机闭环后再决定是否扩展。
