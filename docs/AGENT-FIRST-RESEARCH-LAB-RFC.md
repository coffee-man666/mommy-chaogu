# Agent-first 投研实验室 RFC

> 状态：Draft / 待评审
> 创建：2026-08-06
> 目的：确定 mommy-chaogu 下一阶段的产品主线、首个验证场景与系统边界。
> 本文只回答「为什么做、为谁做、第一步验证什么」；通过评审后，再更新
> `DESIGN.md` 并另写工程实施计划。

## 1. 提议

mommy-chaogu 下一阶段从「多入口行情与投研助手」收束为：

> **本地优先的 Agent-first 投研实验室。用户可以把自然语言观点、文章经验或分析方法交给
> Coding Agent，由 Agent 将其转化为可解释、可复现、可证伪的研究实验，并进一步保存为
> 监控规则，在未来真实数据中持续验证。**

下一阶段的核心产品闭环为：

```text
观点 / 文章 / 经验
        ↓
Agent 提取可验证命题，并澄清歧义
        ↓
检查数据覆盖、时点与可用性
        ↓
生成 ExperimentSpec
        ↓
确定性回测 + 稳健性检验
        ↓
Agent 解读支持证据、反面证据与失效条件
        ↓
保存实验 → 转成监控 → 未来验证 → 进入记忆
```

近期产品资源应优先用于打通这条闭环。Web/TUI 以修复可靠性问题和展示实验产物为主，
暂不继续扩展新的主导航、独立页面和通用策略编辑器。

## 2. 为什么现在收束

项目最有差异化的体验不是某一种界面，而是当行情、资金流、持仓、记忆等数据稳定可用时，
Coding Agent 能自由组合这些能力，自主完成一段研究过程。

过去一个阶段已经补齐安装、配置、Web、TUI、微信、MCP、权限和数据服务等基础设施。
这些工作降低了使用门槛，但继续横向扩展入口的边际价值已经开始下降。下一步需要重新验证
最初的产品假设：**高质量数据与确定性研究工具，能否放大通用 Agent 的投研能力。**

当前代码也已经具备形成闭环的主要零件：

- MCP 与 `mommy-research` Skill 已允许外部 Coding Agent 读取确定性证据包并自主推理；
- 自定义工作流已经可以把自然语言观点编译成可持久化、可校验的 `WorkflowSpec`；
- 回测模块已经具备成本、组合、统一评分、Walk-forward 与 Regime 分析；
- 记忆系统已经能保存研究事件、预测及后续验证；
- 美股日线与指数数据可以避开当前 A 股数据跨境不稳定对实验的干扰。

真正缺少的不是另一个前端，而是连接「观点」与「实验」的领域语义层，以及一个 Agent
可以可靠调用的通用实验运行时。

## 3. 用户与核心任务

### 3.1 第一目标用户

第一阶段服务有投资经验、会表达交易想法，但不一定会编程或使用专业量化框架的主动投资者。
典型特征：

- 会阅读文章、研报、社区讨论或交易书籍，并形成自己的判断；
- 使用均线、通道、量价、事件、基本面等方法，但缺少严谨验证手段；
- 愿意使用 Claude Code、Kimi Code、Cline 等 Coding Agent；
- 关心一个观点何时有效、何时失效，而不只想得到一段行情总结；
- 希望研究资料、实验记录和真实验证留在自己控制的环境里。

### 3.2 核心 Job to be Done

当用户遇到一个看起来有价值的交易观点时，帮助用户在不先学习因子语言、回测框架和数据工程
的前提下，快速完成以下工作：

1. 理解观点究竟声称了什么；
2. 找出无法直接验证的模糊部分；
3. 将其改写为明确、可证伪的实验；
4. 用当时可见的数据运行可信的历史验证；
5. 理解结果、局限与适用环境；
6. 把值得继续观察的实验转成未来监控。

### 3.3 用户承诺

产品承诺帮助用户提升研究能力与验证效率，不承诺发现必然盈利的策略。最终输出必须让用户知道：

- Agent 做了哪些解释和选择；
- 使用了哪些数据及其时间范围；
- 哪些参数由用户提供，哪些是假设；
- 结果在哪些市场环境成立或失效；
- 下一步应该放弃、修改、继续验证还是转成监控。

## 4. 第一条 Golden Scenario

第一阶段只验证一条完整用户故事，不先建设覆盖所有资产和策略的通用平台。

### 4.1 输入示例

> 我认为半导体 ETF 跌破中期均线后，如果在几个交易日内收复均线并重新进入通道，
> 往往是假跌破。请把这个观点形式化，在 SOXX、SMH、QQQ 上测试，比较不同市场环境，
> 并告诉我它什么时候失效。

选择该场景的原因：

- 均线与通道代码已有外部实现可以迁移；
- 该方法来自真实使用经验，能由作者人工判断 Agent 是否理解正确；
- 美股 ETF 日线数据相对稳定，适合先验证产品闭环；
- 场景包含观点理解、参数澄清、技术指标、回测、Regime 和监控，足以暴露核心架构问题；
- 不依赖复杂基本面 point-in-time 数据，也不依赖 A 股实时资金流稳定性。

### 4.2 Agent 应完成的行为

Agent 不应直接猜出一套规则并返回收益率，而应：

1. 识别「中期均线」「几个交易日」「重新进入通道」「持有多久」等歧义；
2. 只询问会实质改变实验结果的问题，并提供合理默认值；
3. 把最终解释展示给用户确认；
4. 生成结构化 `ExperimentSpec`；
5. 检查标的、时间范围、复权、交易日历和指标 warm-up 是否满足要求；
6. 运行包含交易成本与基准的回测；
7. 给出样本数、收益、回撤、胜率、Sharpe，以及 Walk-forward/Regime 结果；
8. 明确过拟合、未来数据泄漏、生存者偏差和样本不足等限制；
9. 输出支持证据、反面证据、失效条件与一个最有价值的后续实验；
10. 经用户确认后保存实验，并允许转成每日监控。

### 4.3 第一版产物

一次完整运行至少产生：

- `ExperimentSpec`：机器可执行、用户可阅读；
- `DataReadinessReport`：数据覆盖、缺口、时间语义与降级说明；
- `BacktestRun`：参数、数据版本、代码版本、结果与逐笔/逐信号记录；
- `ResearchMemo`：Agent 对结果的解释、反证、局限和下一步；
- `MonitorCandidate`：可选的未来监控规则，不自动启用。

第一版允许这些产物是本地 JSON + Markdown，不要求先做 Web 页面。

## 5. 产品原则

### 5.1 Agent-first 不等于让 LLM 做所有事情

- Agent 负责理解意图、提出问题、选择工具、比较结果和解释意义；
- 确定性指标库负责数值计算；
- 回测运行时负责时序、成本、持仓和评价；
- Spec 负责留下可复现、可审计的中间表示；
- Skill 负责约束研究方法、输出结构和风险检查。

任何可重复的计算都不应只存在于 prompt 或模型自由生成的代码中。

### 5.2 先证伪，再优化

Agent 的默认目标是测试观点能否经得起反证，而不是搜索一组最好看的参数。

- 明确区分探索性实验和确认性实验；
- 参数搜索必须记录范围与试验次数；
- 不允许静默优化后只展示最佳结果；
- 保留未通过和失败的实验，避免只记住成功案例；
- 验证集在规则确定后再打开，不能反复用于调参。

### 5.3 事实、假设与推断必须分开

输出必须区分：

- 数据直接提供的事实；
- 用户原始观点；
- Agent 为使观点可执行而提出的假设；
- 回测结果；
- Agent 对结果的推断。

### 5.4 数据质量优先于工具数量

每增加一种数据，必须同时回答：

1. Agent 可以通过什么工具读取它？
2. 历史数据是否具有 point-in-time 语义？
3. 是否能进入研究、回测或监控中的至少一个明确场景？
4. 缺失、过期或失败时如何暴露给用户？

没有命名场景和时间语义的新 API，不进入第一阶段主线。

### 5.5 本地优先与明确授权继续保留

公开市场数据与个人持仓、记忆、写回操作继续使用不同 MCP profile。保存实验、写入记忆、
启用监控等操作必须在用户明确同意后发生。第一阶段不自动下单。

## 6. 系统边界与组件分工

### 6.1 WorkflowSpec 与 ExperimentSpec 分离

现有 `WorkflowSpec` 表达「先调用什么工具，再调用什么工具」，适合通用编排；它不应承担完整的
投资实验语义。新增独立 `ExperimentSpec`：

```text
WorkflowSpec
  └── 编排 compile / validate / run / explain / save 等步骤

ExperimentSpec
  └── 描述 universe / features / entry / exit / sizing / costs / validation
```

初步字段建议：

```yaml
spec_version: 1
id: exp_semicon_false_break_v1
title: 半导体 ETF 均线假跌破
source:
  type: user_viewpoint
  text: "..."
hypothesis: "..."
market: US
universe: [SOXX, SMH, QQQ]
frequency: 1d
date_range:
  start: "2016-01-01"
  end: "2026-07-31"
data_requirements:
  - adjusted_ohlcv
features:
  - type: sma
    window: 20
  - type: price_channel
    window: 20
entry_rule: "..."
exit_rule: "..."
position_sizing:
  type: equal_weight
cost_model: us_equity_default
benchmark: SPY
validation:
  walk_forward: true
  regime_analysis: true
assumptions: []
```

字段的最终形状不在本 RFC 中锁死，Golden Scenario Spike 负责验证哪些字段真正必要。

### 6.2 指标内核

第一批只支持可人工核验、跨数据源复用的确定性指标：

- SMA / EMA；
- 价格通道；
- ATR；
- RSI；
- 成交量均值与放量；
- 标的相对基准强度。

指标实现优先使用本地 OHLCV 统一计算，避免同一指标因上游供应商口径不同而产生不可解释差异。
上游原生指标 API 可以作为交叉校验或降级来源，而不是唯一真相源。

### 6.3 实验运行时

实验运行时负责：

- 读取并校验 `ExperimentSpec`；
- 生成严格按时间可见的特征与信号；
- 执行入场、退出、持仓、成本和基准逻辑；
- 复用现有成本、组合、Walk-forward、Regime 与评分模块；
- 生成可追踪的 `BacktestRun`；
- 禁止 Agent 绕过运行时直接拼接一个无法复现的收益结论。

### 6.4 Agent 与 MCP

第一阶段优先支持 Coding Agent，候选 MCP 能力为：

```text
list_indicators
inspect_data_coverage
validate_experiment
run_backtest
compare_backtests
save_experiment
promote_to_monitor
```

观点到 `ExperimentSpec` 的编译可以先由 `mommy-experiment` Skill 指导当前 Coding Agent 完成；
待 Golden Scenario 稳定后，再判断是否需要内置编译器工具。这样避免为同一个请求重复调用两个 LLM。

## 7. 第一阶段范围

### 7.1 包含

- 美股与 ETF；
- 日线；
- 固定、小规模标的集合；
- 做多；
- 均线、通道与少量基础技术指标；
- 固定持有期、止损止盈、指标条件退出；
- 交易成本与基准；
- Walk-forward 与 Regime；
- 本地实验存储；
- Coding Agent/MCP 入口；
- Markdown/JSON 报告；
- 经确认后转成监控候选。

### 7.2 不包含

- 自动下单或实盘执行；
- 期权、期货、加密货币；
- 高频或逐笔回测；
- 复杂做空、借券成本和保证金；
- 自动寻找最优参数；
- 全市场动态股票池；
- 新的 Web 策略编辑器；
- 文章自动摄取；
- 内幕交易、财报因子等新数据；
- 对未来收益作保证或输出无条件荐股结论。

文章摄取与内幕交易分别作为第二、第三条纵向案例，用来验证底层实验架构是否真正可扩展。

## 8. Golden Scenario Spike

### 8.1 方法

先做一个可丢弃、可人工检查的薄原型，不先建设通用平台：

1. 迁移并核验已有均线/通道代码；
2. 手写第一份 `ExperimentSpec`；
3. 用 SOXX、SMH、QQQ 的真实日线运行；
4. 尽量复用现有回测组件，记录无法复用的原因；
5. 输出 JSON 结果与 Markdown 研究报告；
6. 由 Agent 解读结果并提出一个反证实验；
7. 手工模拟「转成监控」，可以先不接持续任务调度。

Spike 可以包含临时代码，但不得用一个只有作者能理解的 notebook 作为最终证据。输入、输出和运行命令
必须能够由另一个 Coding Agent 重复执行。

### 8.2 Spike 要回答的问题

- Agent 是否能在一次澄清内正确理解该观点？
- `ExperimentSpec` 是否足以表达规则且仍然便于人读？
- 美股日线数据的复权、时间戳和覆盖是否足够？
- 现有回测模块哪些可以复用，哪些仍绑定资金流预测路径？
- 一次运行需要多长时间，结果是否可重复？
- Agent 能否指出反例和数据限制，而不是只总结收益？
- 实验规则是否能无损转成未来监控条件？

### 8.3 通过标准

Golden Scenario 满足以下条件才进入正式工程化：

- 从完整自然语言观点到第一次有效结果不超过 5 分钟；
- 至多一次澄清即可得到用户认可的规则解释；
- 同一 spec、数据版本和代码版本重复运行得到一致结果；
- 输出明确包含样本数、基准、成本、回撤、Walk-forward 与 Regime；
- 数据缺口和所有新增假设对用户可见；
- 至少给出一项支持证据、一项反面证据和明确失效条件；
- 另一名 Coding Agent 只读文档与产物即可重现；
- 结果可以形成监控候选，不需要重新人工翻译规则。

若其中关键条件不成立，应先修正产品假设或缩小场景，而不是继续增加数据源和 UI。

## 9. 后续候选案例

### 9.1 文章 → 可测试方法

用户提供文章或粘贴文本，Agent 将内容拆为：

- 作者事实陈述；
- 交易观点；
- 可验证命题；
- 无法验证或需要额外数据的部分；
- 2～3 个有优先级的实验。

该案例验证的是 Agent 对非结构化经验的吸收能力，以及观点来源到实验结果的可追溯性。

### 9.2 内幕交易 + 技术确认

示例命题：

> 内部人显著净买入后，如果价格重新站上中期均线且行业相对强度改善，未来 20 个交易日
> 是否存在稳定超额收益？

该案例只有在供应商能提供完整历史事件、披露时间和修订语义时才进入回测；只有当前数据时，
可以作为当前研究证据和监控信号，但不得包装为历史验证能力。

### 9.3 基本面与组合构建

基本面、因子模型和 Portfolio Construction 是后续付费价值的重要承载层，但依赖更严格的
point-in-time 财务数据、退市样本、公司行动与估值口径。应在技术面闭环稳定后接入同一套
ExperimentSpec/BacktestRun/Monitor 体系，而不是另建一套产品路径。

## 10. 商业边界假设

开源项目负责让用户能够使用 Agent 完成基础研究闭环：

- 本地 MCP 与 Skills；
- 基础行情连接器和指标库；
- 透明的 ExperimentSpec；
- 单机基础回测、报告、保存与监控。

未来付费能力主要建立在普通用户难以自行获得或维护的部分：

- 稳定、完整、point-in-time 的历史数据；
- 内幕交易、财报、预期、事件和专业因子数据；
- 大股票池、长时间范围和批量实验计算；
- 高级稳健性检验、组合构建与风险模型；
- 专业研究方法包、团队协作和持续监控。

商业价值不应建立在「让 LLM 写几行策略代码」本身，而应建立在可靠数据、可信验证、研究效率
和避免错误结论之上。

## 11. 成功指标

第一阶段不使用下载量或页面访问量作为主要指标，优先观察研究闭环是否真实发生：

- 首次有效实验时间；
- 观点编译成功率与平均澄清次数；
- 相同实验的可重复率；
- 产生支持证据与反证的完整率；
- 每个观点产生的有效实验数；
- 用户主动保存的实验比例；
- 保存实验转成监控的比例；
- 监控后获得真实验证结果的比例；
- 数据缺口、时点错误和 look-ahead 审计问题数。

早期最重要的定性指标是：用户是否因为 Agent 的帮助，完成了过去不会做或嫌麻烦而不做的验证，
并且能够解释结果为什么可信或不可信。

## 12. 文档与决策顺序

本 RFC 评审通过后按以下顺序推进：

1. 确认 Golden Scenario 的规则与外部均线/通道代码来源；
2. 实施薄 Spike，并保存输入、产物和观察记录；
3. 根据 Spike 结果修订本 RFC；
4. 更新 `DESIGN.md` 的项目定位、原则和非目标；
5. 新建 `EXPERIMENT-ENGINE-PLAN.md`，再拆分正式工程阶段；
6. 第一条闭环稳定后，依次验证文章摄取和内幕交易案例。

不在 RFC 通过前编写完整通用引擎，不在 Spike 通过前新增回测 Web 页面。

2. 第一版数据快照如何标识版本，以保证重复运行？
3. 美股默认成本、滑点和 benchmark 应采用什么口径？
4. 监控是否复用现有 signals/alerts，还是需要独立的 experiment monitor adapter？
5. 实验记录放入 `agent.db`，还是新增专门的 research/experiment 数据库？
6. 第一版由 Coding Agent 直接编写 spec，还是复用现有 WorkflowCompiler 扩展一个编译入口？
7. 外部均线/通道代码以依赖、移植还是独立包的方式接入？

## 14. 本次评审需要确认的决定

本 RFC 第一轮只需要确认以下五项：

1. 是否接受「Agent-first 投研实验室」作为下一阶段主线；
2. 是否同意 Coding Agent/MCP 优先，Web/TUI 暂不扩主功能；
3. 是否同意以美股 ETF 日线均线/通道假跌破作为唯一 Golden Scenario；
4. 是否同意 `WorkflowSpec` 与 `ExperimentSpec` 分离；
5. 是否同意先做薄 Spike，成功后才更新 `DESIGN.md` 和编写正式实施计划。

这五项通过，即可开始 Golden Scenario 的规则澄清与代码资产盘点。
